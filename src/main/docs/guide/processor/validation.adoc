If you want to validate a JSON file against your generated JSON Schema, you can inject a bean of type api:jsonschema.validation.JsonSchemaValidator[]. You need the following dependency:

dependency:micronaut-json-schema-validation[groupId="io.micronaut.jsonschema"]

=== Choosing an implementation

Two implementations of api:jsonschema.validation.JsonSchemaValidator[] are available:

[cols="2,3"]
|===
|Artifact |Implementation

|`micronaut-json-schema-validator`
|The built-in validator. It has no third-party dependencies and validates Micronaut's own JSON tree (`io.micronaut.json.tree.JsonNode`), so it works with both https://micronaut-projects.github.io/micronaut-serialization/latest/guide/[Micronaut Serialization] and Jackson Databind. It does not use reflection, which makes it suitable for GraalVM native images.

|`micronaut-json-schema-validator-networknt`
|The https://github.com/networknt/json-schema-validator[NetworkNT JSON Schema Validator] (version 3, on Jackson 3). When it is on the classpath, it replaces the built-in validator.
|===

`micronaut-json-schema-validation` depends on both, so it validates with NetworkNT, as in previous versions.

To use the built-in validator without NetworkNT, depend on `micronaut-json-schema-validator` instead:

dependency:micronaut-json-schema-validator[groupId="io.micronaut.jsonschema"]

This is needed when another library requires a different version of NetworkNT. Both NetworkNT versions use the same `com.networknt.schema` package, so they cannot be on the same classpath. One such library is Apache Camel's `camel-json-validator`, which uses NetworkNT 2 on Jackson 2.

The Micronaut JSON Schema BOM does not manage the NetworkNT version, so it does not force one on your application.

Both implementations pass the same technology compatibility kit (TCK). It covers the behaviour and the messages described below, and runs the official https://github.com/json-schema-org/JSON-Schema-Test-Suite[JSON-Schema-Test-Suite] through the public API. The differences are listed in <<validatorDifferences, Differences between the implementations>>.

=== Validating values

To validate a value against the schema generated for a type, pass the value and the type:

snippet::io.micronaut.jsonschema.test.JsonSchemaValidationExampleTest[tags=validate-type, indent=0]

<1> Validate an object against the schema generated for the `Llama` type. The schema is loaded from the classpath and compiled the first time it is used, then cached.
<2> Each message is prefixed with the https://www.rfc-editor.org/rfc/rfc6901[JSON Pointer] of the invalid value, for example `/name: must be at least 1 characters long`.
<3> The instance location, the failing keyword and the schema location are also available individually.

You can also validate against a schema expressed as a JSON string or as a `Map`:

snippet::io.micronaut.jsonschema.test.JsonSchemaValidationExampleTest[tags=validate-schema, indent=0]

<1> Values can be any object that the application's `JsonMapper` can serialize, a JSON string, or a `io.micronaut.json.tree.JsonNode`. Compiled schemas are cached by their content.

=== Supported specification

The built-in validator implements the following JSON Schema dialects. The dialect is selected with the `$schema` keyword. Schemas without `$schema` use draft 2020-12, the dialect generated by the processor. The NetworkNT validator accepts the 2020-12 dialect only.

[cols="1,3"]
|===
|Dialect |Notes

|https://json-schema.org/draft/2020-12[2020-12]
|All keywords, including `prefixItems`, `$dynamicRef`/`$dynamicAnchor`, `unevaluatedProperties`/`unevaluatedItems` and `$vocabulary` in custom meta-schemas.

|https://json-schema.org/draft/2019-09[2019-09]
|All keywords, including `$recursiveRef`/`$recursiveAnchor`.

|http://json-schema.org/draft-07/schema[draft-07]
|All keywords. `contentEncoding` (base64) and `contentMediaType` (JSON media types) are asserted.

|draft-06, draft-04
|All keywords.
|===

References (`$ref`) are resolved as follows by the built-in validator:

* Within the schema document, using JSON Pointers (`#/$defs/item`), anchors (`$anchor`, `$dynamicAnchor`) and embedded resources identified by `$id`.
* `classpath:` URIs, the default base URI of the generated schemas, are loaded from the classpath.
* URIs that start with the configured base URI (`micronaut.jsonschema.validation.base-uri`, `http://localhost:8080/schemas/` by default) are loaded from the generated schemas folder on the classpath (`META-INF/schemas/` by default). Relative references in schemas without an `$id`, such as `{"$ref": "environment.schema.json"}`, are resolved against the base URI too.
* The meta-schemas of all supported dialects are bundled, so references to `https://json-schema.org/draft/2020-12/schema` and similar work without network access.

The validator never loads schemas over the network.

The `format` keyword is asserted for strings by both implementations, as in previous versions. To use `format` as an annotation only with the built-in validator, set `micronaut.jsonschema.validation.assert-formats` to `false`; it is then only asserted for schemas whose meta-schema enables the 2020-12 format-assertion vocabulary. The NetworkNT validator is configured by its `com.networknt.schema.SchemaRegistryConfig` bean. The following formats are validated: `date-time`, `date`, `time`, `duration`, `email`, `idn-email`, `hostname`, `idn-hostname`, `ipv4`, `ipv6`, `uri`, `uri-reference`, `iri`, `iri-reference`, `uri-template`, `uuid`, `json-pointer`, `relative-json-pointer` and `regex`. Unknown formats are ignored. `idn-hostname` follows IDNA2008, with the Unicode derived properties approximated from Unicode general categories.

Regular expressions (`pattern`, `patternProperties` and the `regex` format) use ECMA-262 syntax and are translated to `java.util.regex` patterns. For example, `$` only matches at the end of the input and `\s` matches Unicode white space.

The built-in validator is verified against the official https://github.com/json-schema-org/JSON-Schema-Test-Suite[JSON-Schema-Test-Suite]. All required and optional tests for draft-04, draft-06, draft-07, 2019-09 and 2020-12 pass, including the optional `format`, `ecmascript-regex`, `bignum`, `float-overflow`, `cross-draft`, `refOfUnknownKeyword` and `dependencies-compatibility` tests. The 2020-12 tests that expect `format` to be an annotation only are run with format assertions disabled.

[[validatorDifferences]]
=== Differences between the implementations

The TCK runs the official JSON-Schema-Test-Suite (draft-07, 2019-09 and 2020-12, required and optional tests) through api:jsonschema.validation.JsonSchemaValidator[] for both implementations. It leaves out the tests that need the remote documents of the test suite, and the 2020-12 tests that expect `format` to be an annotation only. The built-in validator passes all the other tests. The NetworkNT validator differs as follows:

* It only accepts schemas of the 2020-12 dialect. Schemas that declare another `$schema` fail with an "Unknown dialect" error.
* It does not pass 74 optional tests, all edge cases of the `format` keyword (mostly `hostname`, `idn-hostname` and `email`) and of ECMA-262 regular expressions. For example, `\s` does not match Unicode white space, and some invalid host names are accepted.
* An invalid JSON string to validate is reported with an unchecked exception, whereas the built-in validator throws an `IOException`.

The TCK checks that both report the same messages, in the same format (`<JSON Pointer>: <message>`), for the cases it covers. The details of the messages of composite keywords such as `anyOf` and `oneOf` can differ.
