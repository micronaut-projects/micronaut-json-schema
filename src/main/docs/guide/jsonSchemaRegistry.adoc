[[jsonSchemaRegistry]]

The Micronaut JSON Schema Registry module reconciles JSON Schemas between one authority source and configured targets at runtime.

The registry supports three authority modes:

* `application`: discover application classes annotated with api:jsonschema.JsonSchema[] and resolve their generated JSON Schemas
* `csr`: read the latest JSON Schema from Confluent Schema Registry subjects
* `oracle`: read JSON Schemas from configured Oracle authority discovery providers

The non-authoritative systems are reconciled as targets. Schema Registry can register missing or changed subjects. Oracle materializers can create missing configured artifacts and report drift for existing artifacts.

== Dependency

To use runtime reconciliation, add the registry module:

dependency:micronaut-json-schema-registry[groupId="io.micronaut.jsonschema"]

Application authority mode also requires the normal JSON Schema annotation processor setup so schema resources are generated during compilation.

== Enabling the Registry

The registry is disabled by default. Enable it with `micronaut.jsonschema.registry.enabled`:

[configuration]
----
micronaut:
  jsonschema:
    registry:
      enabled: true
      authority: application
----

When enabled, the registry runs once on startup. Startup failure handling is controlled by `micronaut.jsonschema.registry.fail-fast-strategy`:

* `readiness_gate`: record the failure and keep readiness down until a later successful run
* `startup_abort`: fail application startup when startup reconciliation fails
* `none`: record the failure and continue without gating readiness

The registry also exposes api:jsonschema.registry.JsonSchemaRegistryService[], which can trigger the same reconciliation logic programmatically.

== Authority Modes

Application authority discovers api:jsonschema.JsonSchema[] types and resolves their generated schemas through api:jsonschema.JsonSchemaMapper[].

[configuration]
----
micronaut:
  jsonschema:
    registry:
      enabled: true
      authority: application
      csr:
        enabled: true
        url: http://localhost:8081
      oracle:
        enabled: true
        datasource: default
----

Schema Registry authority uses configured subjects when `micronaut.jsonschema.registry.csr.subjects` is set. Otherwise, it discovers subjects from `GET /subjects` and keeps subjects that start with `micronaut.jsonschema.registry.naming.subject.prefix`.

When Schema Registry is used, the registry uses these Confluent Schema Registry API calls:

* subject enumeration: `GET /subjects`, filtered client-side by `micronaut.jsonschema.registry.naming.subject.prefix`
* authority or target latest schema lookup: `GET /subjects/{subject}/versions/latest`
* target mode check before writes: `GET /mode/{subject}`, falling back to `GET /mode` when the subject mode is not set
* compatibility check before registering a changed target schema: `POST /compatibility/subjects/{subject}/versions/latest`
* target registration: `POST /subjects/{subject}/versions` with `schemaType=JSON`

HTTP 5xx and HTTP 429 responses are retried with a bounded retry policy. Other HTTP 4xx responses are not retried.

[configuration]
----
micronaut:
  jsonschema:
    registry:
      enabled: true
      authority: csr
      csr:
        enabled: true
        url: http://localhost:8081
        subjects:
          - com.acme.Order
----

Oracle authority uses configured Oracle authority discovery providers. If none are configured, the built-in JSON Domain discovery provider is used.

[configuration]
----
micronaut:
  jsonschema:
    registry:
      enabled: true
      authority: oracle
      oracle:
        enabled: true
        datasource: default
        domains:
          - APP_COM_ACME_ORDER
----

== Schema Registry Target

Schema Registry is enabled with `micronaut.jsonschema.registry.csr.enabled=true`.

When Schema Registry is a target:

* `manage` registers a missing subject or a new version when the latest schema differs
* `observe_only` reads the latest subject and reports `missing_target`, `equivalent`, or `drift`

Schema Registry writes are skipped when `micronaut.jsonschema.registry.dry-run=true`; outcomes are labelled with `[DRY-RUN]`.

The registry can authenticate to Schema Registry using:

* `micronaut.jsonschema.registry.csr.username` and `micronaut.jsonschema.registry.csr.password`
* `micronaut.jsonschema.registry.csr.bearer-token`
* `micronaut.jsonschema.registry.csr.headers.*`

Bearer authentication takes precedence over basic authentication when both are configured.

== Oracle Authority and Materialization

Oracle integration requires `micronaut.jsonschema.registry.oracle.enabled=true` and a `javax.sql.DataSource` bean. The datasource bean name is selected with `micronaut.jsonschema.registry.oracle.datasource`; the default is `default`.

Oracle integration has two roles:

* authority discovery providers read existing Oracle-backed JSON Schemas when `authority=oracle`
* materializers reconcile a candidate schema to Oracle artifacts when Oracle is a target

If `micronaut.jsonschema.registry.oracle.authority.providers` is not configured, the built-in domain authority provider is used. If the provider list is configured, the configured list replaces the default list.

If `micronaut.jsonschema.registry.oracle.materializers` is not configured, the built-in JSON Domain materializer is used. If the materializer list is configured, the configured list replaces the default list.

The built-in domain provider supports explicit selection through `micronaut.jsonschema.registry.oracle.domains`. When no explicit domain list is configured, it applies `micronaut.jsonschema.registry.naming.domain.prefix` as a prefix filter.

The built-in domain authority provider enumerates domains from the resolved Oracle data dictionary view. The query always orders by `name`; an explicit domain list is pushed down as `IN` predicates, while the configured domain prefix is pushed down as a `LIKE` predicate:

[source,sql]
----
SELECT name FROM USER_DOMAINS [WHERE name IN (?) | name LIKE ?] ORDER BY name
SELECT name FROM ALL_DOMAINS WHERE owner = ? [AND name IN (?) | AND name LIKE ?] ORDER BY name
----

When `micronaut.jsonschema.registry.oracle.domains` is set, those configured names are used as the selected set and uppercased before lookup. When no explicit domain list is set, the prefix filter is `micronaut.jsonschema.registry.naming.domain.prefix` uppercased plus `%`.

For each selected domain, schema extraction uses this order:

1. `SELECT dbms_metadata.get_ddl('SQL_DOMAIN', ?) FROM dual`, or `SELECT dbms_metadata.get_ddl('SQL_DOMAIN', ?, ?) FROM dual` when `owner` is configured
2. `SELECT search_condition FROM user_domain_constraints WHERE domain_name = ?`, or `SELECT search_condition FROM all_domain_constraints WHERE owner = ? AND domain_name = ?` when `owner` is configured

The provider extracts the JSON text from either `VALIDATE USING` or `VALIDATE CAST USING`, unescapes doubled single quotes, parses the text as JSON, and logs whether `get_ddl` or `search_condition` was used. Large schemas created by the built-in materializer are reconstructed from `to_clob('chunk') || ...` expressions. CAST mode is retained as part of the discovered domain representation.

The built-in domain materializer computes domain names from logical schema names by prepending `micronaut.jsonschema.registry.naming.domain.prefix`, replacing `.` with `_`, and uppercasing the result. If the computed identifier is longer than 128 UTF-8 bytes, it is truncated and suffixed with `_` plus the first 8 uppercase hex characters of the SHA-256 hash of the full computed name.

In Oracle authority mode, built-in domain names are paired to Schema Registry subjects through `micronaut.jsonschema.registry.mappings` when the domain name cannot be reversed deterministically. Names that include `_`, truncation, hash suffixing, or case-sensitive Java-style package names require an explicit mapping.

The built-in domain materializer uses strict validation by default. Configure `micronaut.jsonschema.registry.oracle.cast-mode=cast` to enable Oracle CAST validation, or set `options.castMode` on a configured built-in domain materializer to override the default. Strict and CAST domains with otherwise identical schema text are reported as drift.

The built-in duality-view discovery provider resolves `USER_`, `ALL_`, or `DBA_` metadata and retrieves each view name and its raw `JSON_SCHEMA` value in one ordered query. The same include, exclude, and prefix filtering rules are applied to `view_name`:

[source,sql]
----
SELECT view_name, json_schema FROM USER_JSON_DUALITY_VIEWS [WHERE view_name IN (?) | view_name LIKE ?] ORDER BY view_name
SELECT view_name, json_schema FROM ALL_JSON_DUALITY_VIEWS WHERE owner = ? [AND view_name IN (?) | AND view_name LIKE ?] ORDER BY view_name
SELECT view_name, json_schema FROM DBA_JSON_DUALITY_VIEWS WHERE owner = ? [AND view_name IN (?) | AND view_name LIKE ?] ORDER BY view_name
----

`USER_` metadata is used when no owner is configured. With an owner, `ALL_` metadata is tried first and `DBA_` metadata is used as a fallback when appropriate.

== Oracle Extensions

Authority discovery providers use the shared schema discovery SPI from the generator module:

[source,java]
----
public interface SchemaDiscoveryProvider {
    String providerId();
    DiscoveryResult discover(SchemaDiscoveryContext context,
                             SourceSpec source) throws Exception;
}
----

Registry provider resolution supports Micronaut beans and `ServiceLoader` entries for:

[source]
----
META-INF/services/io.micronaut.jsonschema.generator.discovery.SchemaDiscoveryProvider
----

Custom provider configuration is passed through `providerClassName`, optional `owner`, and provider-specific `options`:

[configuration]
----
micronaut:
  jsonschema:
    registry:
      enabled: true
      authority: oracle
      oracle:
        enabled: true
        authority:
          providers:
            - name: duality-views
              providerClassName: example.oracle.OrderDualityViewDiscoveryProvider
              options:
                logicalFqcn: com.acme.Order
                subject: com.acme.Order
                viewName: ORDER_DV
----

Materializers implement api:jsonschema.registry.oracle.OracleSchemaMaterializer[] and are resolved as Micronaut beans or `ServiceLoader` providers matched by `providerClassName`.
The materializer SPI exposes `representationDescription()` so implementations can describe the Oracle artifact representation they support. The registry still calls `projectionCompatibility(...)` for each candidate before materialization.

`ServiceLoader` materializers are registered through:

[source]
----
META-INF/services/io.micronaut.jsonschema.registry.oracle.OracleSchemaMaterializer
----

The registry includes a duality-view materializer, `io.micronaut.jsonschema.registry.oracle.OracleDualityJsonViewMaterializer`. It verifies existing JSON Relational Duality Views by reading Oracle duality-view metadata and comparing normalized schema text. It can create a missing view only when `options.viewDdl` or `options.viewDdlResource` supplies explicit DDL. Existing views are never replaced or mutated.

== Drift and Projection Compatibility

Before reconciling a schema to Oracle, each materializer checks whether its Oracle artifact model can represent the candidate schema exactly. If exact representation is not possible, the registry reports `projection_incompatibility`.

Oracle-specific schema metadata such as `extendedType`, `sqlPrecision`, and `sqlScale` cannot be projected to CSR without weakening validation semantics and is reported as `projection_incompatibility`.

Oracle materializers are create-missing only in this version:

* missing target + `manage`: create the configured artifact
* missing target + `observe_only`: report `missing_target`
* existing equivalent artifact: report `equivalent`
* existing different or unreadable artifact: report `drift`

Existing Oracle artifacts are not altered, replaced, dropped, or migrated.

`micronaut.jsonschema.registry.oracle.drift.mode` controls whether drift is treated as a reconciliation failure:

* `report`: report drift without marking the outcome as a failure
* `fail`: report drift and mark the outcome as a failure

== Mapping

The registry derives names from configured naming rules where possible. Explicit `micronaut.jsonschema.registry.mappings` entries are available as a built-in domain pairing shortcut:

[configuration]
----
micronaut:
  jsonschema:
    registry:
      mappings:
        - subject: com.acme.Order
          domain: APP_COM_ACME_ORDER
----

Mappings are used to override or disambiguate subject/domain pairing. They are not a generic mapping format for every Oracle artifact kind. Non-domain providers and materializers should define their mapping options under their own `options`.

== Readiness and Metrics

When Micronaut Management is present, the registry exposes a readiness indicator backed by the last reconciliation state. Health checks do not query Schema Registry or Oracle directly.

When Micrometer is present, the registry records:

* reconciliation outcomes
* discovered authority schema counts
* reconciliation run duration
* target operation duration for Schema Registry HTTP operations and Oracle introspection/DDL operations

Metrics avoid high-cardinality schema identifiers. Schema names, subjects, and Oracle artifact names are logged in structured reconciliation outcome messages.
